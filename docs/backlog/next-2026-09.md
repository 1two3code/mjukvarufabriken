Written the evening the first Ögonblick build reached a live URL through the full gated pipeline
(run 7 + redeliveries + run 8; docs/LEARNINGS.md). Hasse's ask: "what are the obvious next steps
on the mjukvaruhuset idea and the single-use software idea." This is the ranked answer, turned into
briefs. Decisions already locked in [strategy-2026-08-31.md](strategy-2026-08-31.md) and
[single-use-software.md](single-use-software.md) are not re-litigated here — this doc is about
*what to build next and in which order*, given where the code actually is.

## The one-paragraph read of the situation

Runs 1–7 each died to something nobody predicted; every fix earned by a real run was cheap and
correct, while much of what was built speculatively ahead of the runs was expensive and
wrong-shaped. The harness is now ahead of the shop front: the pricing ladder is decided and seeded,
but no customer can *walk* it — there is no no-login spec chat, no voucher order, no demo gallery,
no hosting window, no footer in the delivered apps. Meanwhile one app has taken nine attempts and
no second app has been through at all. So: (1) run a second and third spec through the pipeline
before designing more harness features, (2) build the customer-facing rungs of the ladder, which
is mostly api/portal/site work and does not touch the harness, (3) keep the untrusted-traffic gate
list honest before any ad spend.

## Hasse's notes (docs/HASSE-NOTES.md), answered

- **Why no GitHub Actions deploy in the delivered repo?** By design for the preview stage: the
  delivered repo ships a lint+test CI only (wave 7 curation), and deployment runs through our
  CodeBuild → ECR → ECS Express path because preview apps live on our infra. A customer-owned deploy
  pipeline is the M11 vended-account story (dev/qa/live in *their* account), not a preview concern.
- **Should an order have many jobs, each job many builds?** The redeliver mode already made an
  order hold several jobs of different kinds; a job = one container run with typed steps and
  retries inside it. "Job with many builds" would duplicate that. S5 makes the history visible:
  order → jobs (build / redeliver / later export), each with its step timeline and retry chain.

## Decisions taken tonight without Hasse (revisit if wrong)

- Demo builds wait for admin approval *after* payment, not before (the customer pays 500 kr, the
  admin approves within the weekly cap, the build starts). Alternative — approve before payment —
  means an unpaid queue; rejected for now.
- Hosting windows: demo 14 days, real build 30 days, both admin-extendable. The managed
  subscription (600 kr/mo) is the "extension" product; until it is billable, an admin extends by hand.
- Export format for the app database is JSON per table, not a `pg_dump` (no binary in the api
  image; JSON is loadable anywhere). A proper dump can come with the job image later.
- The footer never fails a delivery. If a worker removes it, the live check records it and
  HANDOVER says so; the fix is a template/prompt change, not a failed customer build.
