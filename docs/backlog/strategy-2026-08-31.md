## Business thesis
- **The build is the on-ramp; the subscription is the business.** Long-term: help SMBs get into
  agentic software development (Claude Code), with us as scaffolding + support + tooling.
- Two customer stages, supported as tiers: **#1 Managed** (we drive; customer emails/chats what
  they want) → **#2 Co-pilot** (they drive Claude Code themselves; we're support + infra +
  guardrails). Graduation #1→#2 is expected and welcome; **ejection is by design** (vended
  account leaves with the customer). The easier agentic dev gets, the wider our funnel — the
  trend is the growth engine, not the threat.

## Pricing ladder (ex moms; replaces S/M/L 15k/45k/120k)
1. **Free** — spec chat → fixed quote (+ possibly a mockup). No build on the free tier.
2. **~500 kr** — voucher demo build ("give us one of your problems"). Token cost to us ≈ 60–80 kr.
3. **Internal ~$50 top-up** — for a demo that lands well, we spend our own tokens to push it to
   an impressive MVP. Loss-leader, admin's manual call (not a customer-facing SKU).
4. **~3–5k kr** — real build, hosted. Hard ceiling stays 5 000 kr for now.
5. **Managed subscription: 600 kr/mo** — hosting + support + resident availability.
   - Resident tokens **on top, metered ×1.5** (option A — billing path already built). No
     included allowance to start; revisit if bills feel naggy.
   - Upgrades/extra AWS resources built via resident carry their own bill: **AWS cost
     passthrough +20 %** (exact per-customer figure falls out of the vended account's
     consolidated billing — M12 phase 2).
   - **Co-pilot tier pricing: deferred** until M11 dev-env design; likely lower base + same
     ×1.5 tokens.
- Payment mechanics (leaning, not hard-locked): full payment upfront below ~3k; 50/50
  deposit/balance split only above. Existing logged-in customers ordering app #2+ get a
  frictionless flow (no silly small upfront).

## Go-to-market (goal: 40 monthly paying customers)
- **No warm SMB network** → the machine generates its own proof:
  - **Demo gallery**: 5–8 live, clickable demo apps of different problem shapes (~100 kr each
    to produce) on the public site. The factory is the marketing department.
  - **Dogfood case studies** with honest numbers (build time, cost).
- **Don't compete with platform SaaS** (Bokadirekt, Foodora, Shopify): the product is *custom
  at 500 kr* — the Excel-sheet/paper-binder/WhatsApp workflows platforms never build
  (hantverkare job tracking, small-B2B order intake, förening admin, verkstad status flows).
  Secondary restaurant angle: "stop paying Foodora 30 %" — real but harder.
- **Voucher = discovery machine**: run the broad "one of your problems, 500 kr" offer first;
  verticalize whatever recurs across the first 15–20 demos into targeted ads (IG/FB, Swedish
  SMB niches). First ad experiment ≈ 5 000 kr budget. Landing → **spec chat with no login**
  (login only to save/receive the demo). Voucher demos capped per week, admin-approved.
- Rough unit economics: impressed-demo conversion ~1/5 → CAC ≈ 500–1 000 kr → payback ≈ 2 mo
  of subscription.
- **Sequencing (prerequisites, from the standing bans):** cold ad traffic = untrusted
  customers, and 40 cheap-tier customers can't get hand-held QA. Therefore:
  1. Dogfood (trusted specs, safe now) → case studies + demo gallery
  2. Close Gate B (C1 egress fence, D1 spend metering) + Gate C essentials + deploy live
  3. Ad experiment → verticalize winners
- Hasse's two "all types of anything" business contacts: low-priority coffee-chat discovery,
  good internal-chaos profiles, zero cost.

## Delivery-quality direction (Gate C approach — agreed 2026-08-31)
Framing: the pipeline verifies proxies; nobody visits the URL as the customer will. Fix that,
don't add more proxy gates (the review gate already produced one false-positive build failure).
Ranked work order:
1. **Real end-to-end acceptance check**: post-deploy, headless-render the delivered app at its
   live URL and exercise acceptance criteria against it (auth included); fail closed on an
   empty/undiscoverable probe surface. Covers the guestbook/401/render/publicUrls class.
2. **DB provisioning for delivered apps** (audit D1): apps needing persistence never get a DB
   today — hard blocker for the SMB problem-app strategy.
3. **Gate-on-merge**: stop trusting git's exit code; build/test after each merge (or merge to an
   integration branch, fast-forward on green).
4. **Cheap-tier pragmatism**: failed demo build auto-retries once before paging a human
   (rebuild ≈ 100 kr).

## M11 dev-env edit-LLM fence (agreed 2026-08-31)
Don't define "aesthetic changes" — define a **path allowlist**:
1. **Hard fence (enforced, not prompted):** edit tool writes only inside allowlisted paths
   (locales, `**/*.css`, `public/`, component markup); never api/auth/DB/config/migrations.
   Deny by default.
2. **Soft fence:** scoped system prompt on top — UX, not security.
3. **Escape valve:** out-of-fence requests aren't refused; they become an iteration brief →
   the normal gated harness build (docs/backlog/dev-escalation.md). Fence-crossing requests
   are the upsell moment. A too-strict fence costs nothing — it just escalates.
