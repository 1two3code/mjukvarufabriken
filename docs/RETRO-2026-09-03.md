# Retro — nine runs to the first green delivery (2026-09-01 → 2026-09-03)

On 2026-09-03 the factory took one frozen spec, planned it, built it with parallel workers, passed
five gates, pushed a repository, provisioned a database, an S3 prefix and an IAM role, stood the app
up on ECS Express, judged it with a real browser and handed over a URL — **in a single pass, with
nobody intervening**. The gallery was then exercised by hand: upload 201, list 200, thumbnail served
through a presigned URL.

This is the retro on how the previous eight runs got us there, what the failures actually taught,
and what is *not* proven yet. Per-defect detail stays in [LEARNINGS.md](LEARNINGS.md); costs stay in
[../TOKENS.md](../TOKENS.md). This file is the synthesis.

### Three things this table says

**The failure frontier moved outward every single time.** Sandbox → our api wiring → template →
generated code → merge repair → template → infra IAM → the gate's own renderer → green. No run ever
failed at a phase an earlier run had already passed. That is the evidence that the fixes were fences
rather than patches: nine runs, zero regressions.

**Only one of nine failures was the model writing bad code.** Run 4 — a route prefix mismatch, caught
by the review gate before anyone saw it. The other eight were our machinery: proxy, service wiring,
template defaults, merge repair, IAM, the acceptance renderer. For a product whose pitch is "an AI
writes your app", the load-bearing insight is that **generation was never the bottleneck**. The rails
around it were, and rails are ordinary software that gets permanently better.

**The expensive failures were the late ones.** Runs that died in a gate cost USD 11–20 and ~90
minutes each. Runs that died in delivery cost the same *and* had already produced a working
repository. That asymmetry is what justified the single highest-leverage thing built in these three
days (below).

## What the two post-handover defects taught (the real lesson of the week)

Run 8's delivery went green, the URL worked, and the next morning the backend answered 500. Then a
second 500 after that was fixed. Both are worth more than the eight build failures combined, because
both had passed every gate.

1. **Stale database password.** Redelivery re-keys the app's database role (the platform never stores
   the password); the deploy step found the Express service "already exists" and only *described* it,
   so the container kept the old `DATABASE_URL`. Pooled connections stayed authenticated long enough
   for the live check and every manual curl to pass. It failed when the pool recycled — hours later.
2. **jsonb encoded twice.** The store bound `JSON.stringify(value)` to a `$3::jsonb` parameter; the
   `postgres` driver, learning from the prepared statement that the parameter is jsonb, stringified
   it again. Reads came back as JSON *text*. Invisible to every unit test, because the fake `query`
   recorded the parameter and never handed it to a driver.

Both share one shape: **two behaviours, each correct in isolation, composed wrongly at a boundary we
had faked.** And both would have been caught before handover by the same two cheap probes:

- the live check **writes then reads** instead of only GETting an empty database;
- the live check opens a **fresh** connection (or the app's `/health` touches the database) instead
  of riding a warm pool.

The standing rule this earns: *a test double verifies our logic, never theirs.* Every boundary the
factory crosses — the Postgres driver, IAM, ECS, a browser — needs at least one test against the
real thing. We have that for the browser (run 8's fix) and for IAM (the infra security-baseline
tests). We do not have it for the database driver.

## The best thing we built: the redeliver path

Run 7 proved the build half and then failed in delivery. Rebuilding to test a one-line IAM fix costs
~USD 17 and ~90 minutes. `POST /bff/orders/:id/jobs/redeliver` (#107) re-runs only the delivery half
of an already-delivered repository: **~USD 0.10–0.20, ~3 minutes.**

Nine redeliveries then found nine hosting defects for about one dollar. As rebuilds that iteration
would have cost ~USD 150 and most of two days. The generalisable move: **when a pipeline has a cheap
half and an expensive half, buy the split before you start debugging the expensive one.**

## Money, honestly

A delivered M-class app costs **~USD 15–20 in job tokens**, ~90 minutes wall clock. Cumulative
project spend is ~USD 2 725 — overwhelmingly the factory building *itself*, not the factory running.
Run 9 was the cheapest build of the nine (USD 15) *and* the only green one, which is the shape you
want: fences don't just prevent failures, they stop paying for rework.

## Version policy (proposed, and why this is v0.1.0)

- **`v0.1.0`** — the machine works once, end to end, on our own order, in dev. ← tagged 2026-09-03
- **`v0.2.0`** — repeatable: two further apps of *different* classes (S, L), each green in a single pass.
- **`v0.3.0`** — a `live` environment exists and a real card is charged through it.
- **`v1.0.0`** — someone who is not us pays real money and gets a working URL. Reserve it for that.

Calling today 1.0 would be lying to ourselves about five things: M10 (Proof) has zero of two boxes
ticked, apps #2 and #3 are unbuilt; there is no `live` environment (M11 is not started); Stripe is
test-mode only, pending account activation; delivery still runs through a personal GitHub App
install; and n = 1 — the factory has gone green exactly once, on the app it was debugged against.

## What is not proven

- **Repeatability across spec classes.** Ögonblick is one M-class PWA that nine runs were tuned
  against. The advent calendar (S) and Netlab arcade are the actual proof.
- **Durability of a delivery.** The first green handover broke overnight. Nothing watches a
  delivered app; nothing alerts on a failed deploy.
- **Teardown and cost control.** Runs 7 and 8's preview services, databases and roles are still
  running in dev. #123 built the machinery; it has never been pointed at anything.
- **Customer-visible honesty.** "Delivered" without a URL recurred ten times. Wave 14 graduated a
  fix (`hosting: live | unhosted | none`, a reason on the job, "Deliver again" in the portal) — it
  has not yet been observed on a real run.
- **Unattended operation.** Every one of these nine runs had a human watching CloudWatch.

## Before run 10, in order

1. **Write-then-read + fresh-connection probes in the live acceptance check.** Both post-handover
   defects would have been caught pre-handover, at zero token cost.
2. **One template-store test against a real Postgres** (CI service container — there is no docker in
   this WSL distro, so it is CI-only). The two defects that fakes could not see both lived here.
3. **Point the teardown machinery at this order's stale previews**, and give an order a preview
   budget so a forgotten service can't run forever.
4. **Verify the `unhosted` status wording on a real run** — it is graduated but unproven.
5. **Then run 10 as a different class** (the S-class advent calendar), because repeatability is the
   thing 0.2.0 is waiting on — not another Ögonblick.
