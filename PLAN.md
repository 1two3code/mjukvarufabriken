Full spec, ready to feed into the normal order/spec flow (or seed directly):
    - **Goal:** An online ordering site for a neighbourhood bakery so customers can pre-order bread and pastries for pickup and pay in advance, with a staff-facing view of the day's orders.
    - **Users:** Regular customers pre-ordering for weekend pickup; bakery staff managing the production queue each morning; the owner reviewing daily sales.
    - **Features** (title — description — acceptance criteria):
      1. Product catalog — bread/pastries/cakes with photos, prices, daily availability — sold-out items marked and un-orderable; prices shown in SEK incl. moms.
      2. Checkout with card and Swish — pay via Stripe at checkout — payment must succeed before an order is confirmed; customer gets a confirmation with pickup time; a failed payment leaves the order unconfirmed and retryable.
      3. Customer accounts — log in to see past orders and reorder in one click — reorder without re-entering items; order history scoped to the logged-in customer only.
      4. Staff production view — the day's orders as a production queue, separate from sales — staff accounts see/update only the queue, not sales figures or settings; marking an order "ready" emails the customer.
      5. Owner sales dashboard — daily/weekly totals by product — only owner-role accounts can open it.
      6. Bookkeeping integration — confirmed sales sync to Fortnox daily — a day's sales appear in Fortnox by next morning with no manual entry; a failed sync retries and flags the owner if it keeps failing.
      7. Loyalty stamp card — every tenth pre-order gets a free pastry — stamp count visible on the account; the tenth order auto-applies the free item.
      8. Pickup time slots — capped per slot — a full slot stops accepting orders; customers see only open slots.
    - **Non-goals:** No delivery (pickup only in v1); no multi-location support; no public API for third parties.
    - **Stack constraints:** Must integrate with the bakery's existing Fortnox account for bookkeeping; payments in SEK only, card and Swish via Stripe.

## Decisions (made 2026-08-26, change here if you disagree)
- Cloud: AWS (CDK for IaC, eu-north-1 Stockholm)
- Agent runtime: Claude Agent SDK (TypeScript), build jobs in Docker on ECS Fargate
- Payment: Stripe Checkout (Klarna/cards come through Stripe). Test mode until live verification clears. **Merchant of record (decided 2026-08-28): we are our own MoR** — we itemize + remit the 25 % VAT line ourselves and offer `card + klarna` explicitly (`payment_method_types`) with Stripe **Managed Payments disabled per session** (its MoR default was also hiding Klarna on the unactivated sandbox). Live Klarna/card needs account activation (org.nr + bank).
- Stack: `templates/web` — npm-workspaces TS monorepo extracted clean-room from uptool-pwa: React 19 + Vite + RTK Query SPA, Fastify 5 BFF (Zod 4), CDK. Used for the factory portal/site AND as the golden template every customer build starts from. Postgres (RDS), S3 for artifacts
- Auth: email magic link (BankID = later)
- Delivery target: GitHub repo — we create a GitHub org/account for the customer during onboarding if they lack one, then transfer (decided 2026-08-26). Hosting (revised 2026-08-28): **ECS Express Mode** in eu-north-1 (App Runner stops taking new customers 2026-04-30 and AWS points to Express Mode; App Runner isn't in eu-north-1 anyway). Express Mode gives a Fargate service + auto HTTPS URL + shared ALB, but takes a prebuilt ECR image — so delivery builds the customer image (CodeBuild → ECR) then creates the service. Static/no-backend apps → S3 + CloudFront instead. No GitHub connection needed (that was App Runner's source build)
- Languages: sv + en on both the public site and the portal from v1 (decided 2026-08-26)
- Pricing v1: S/M/L = 15k / 45k / 120k SEK ex moms (decided 2026-08-26); fixed price per accepted spec, 50% deposit before build, 50% on delivery; resident-agent mode = tokens × 1.5 + monthly fee. Resident agent v1 runs on the customer's own Anthropic key once deployed in their account (decided 2026-08-26)
  - **Under revision (2026-08-30, NOT decided yet — do not build against this).** Hasse's original concern: 120k for L is priced like a traditional agency project a small business didn't ask for, and drags in approvals/expectations/red tape that kill the sale before it starts (compute cost is trivial either way — ≈1,000 SEK at the L budget, ≈$2.5/M budget-tokens measured).
    - **Widened 2026-08-30 (later): a deeper rethink, not just a cheap tier bolted under S.** Direction being explored — a ladder of very cheap, low-risk steps instead of S/M/L:
      1. A **free tier** (shape TBD).
      2. A **very low entry tier**, "a few hundred SEK" (~$50) — basic demo value only.
      3. If that demo lands well, mjukvaruhuset **spends another ~$50 of its own token budget** (not necessarily billed to the customer yet) to push the demo into something that actually reads as an impressive MVP — a deliberate loss-leader step to make the *next* sale easy, not a customer-facing SKU.
      4. Upsell from an impressed customer to a mid-tier order, **$300–500** — note this is far below current M (45k SEK ≈ $4,300) and L (120k SEK ≈ $11,500), even below current S (15k SEK ≈ $1,400). The existing S/M/L ladder is not what this replaces down to; it's a different, much cheaper ladder.
      5. A **subscription for LLM-powered edits** — the recurring-revenue tier, and the likely billing home for M11's dev-env resident LLM.
    - **Hard ceiling for now: nothing offered above 5,000 SEK.** Explicit "let it grow" philosophy — prove the software already saves/makes the customer money first, then they seek out more features/orders themselves, rather than extracting a big upfront price on a sale that hasn't proven anything yet.
